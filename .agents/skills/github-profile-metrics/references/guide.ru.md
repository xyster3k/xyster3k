# Страница GitHub с динамикой публичных и приватных проектов

Это инструкция по созданию страницы по образцу [профиля xyster3k](https://github.com/xyster3k). Она описывает устройство страницы, сбор статистики, доступ к приватным репозиториям, обновление, историю показателей и проверку результата. Оформление можно выбрать самостоятельно.

## 1. Проверенный пример

На 5 ноября 2026 года профиль `xyster3k` использует публичный репозиторий `xyster3k/xyster3k`, корневой `README.md`, генератор на Python и ежедневный сценарий GitHub Actions. Публикуются два файла: структурированные данные в формате JSON и карточка в формате масштабируемой векторной графики SVG.

Проверка опубликованного результата:

| Показатель | Значение |
| --- | --- |
| Время формирования | 2026-11-05 10:52:42 UTC |
| Период активности | 365 дней |
| Доступные репозитории после исключения архивов | 72 |
| Публичные репозитории | 9 |
| Приватные репозитории | 63 |
| Репозитории с отправкой изменений за период | 63 |
| Авторские коммиты по поиску GitHub | 9 406 |
| Созданные запросы на слияние | 55 |
| Состояние сбора | `setup_needed=false` |
| Полнота поиска коммитов по ответу GitHub | `commit_search_incomplete=false` |

Последние пять ежедневных запусков завершились успешно. [Проверенный запуск](https://github.com/xyster3k/xyster3k/actions/runs/42014320009), [публичные данные](https://raw.githubusercontent.com/xyster3k/xyster3k/main/assets/private-metrics.json) и [карточка](https://raw.githubusercontent.com/xyster3k/xyster3k/main/assets/private-metrics.svg) позволяют проверить путь обновления. Ссылки на файлы показывают текущую версию, поэтому числа со временем изменятся.

Карточка содержит сводку за скользящий год. Для истории изменений показателей предусмотрен отдельный способ, описанный в разделе 11.

## 2. Устройство системы

Последовательность работы:

```text
GitHub Actions по расписанию или вручную
    |
    | GH_METRICS_TOKEN читает разрешённые данные
    v
Генератор Python обращается к API GitHub
    |
    | Собирает сводные показатели в памяти
    v
assets/private-metrics.json + assets/private-metrics.svg
    |
    | Проверка допустимых полей и состояния сбора
    v
GITHUB_TOKEN записывает только готовые файлы в репозиторий профиля
    |
    v
README показывает SVG посетителю
```

Сборщик обращается к программному интерфейсу GitHub (API) с токеном доступа к выбранным проектам. Посетитель получает готовую картинку. Работа страницы опирается на GitHub Actions и хранение файлов в Git; отдельный сервер для такой карточки не требуется.

Формат JSON удобен для проверки источников, создания другого оформления и дальнейшего построения графиков. Формат SVG подходит для вставки в README как изображения. Текст SVG создаётся средствами стандартной библиотеки Python.

## 3. Формат страницы

Выберите место публикации:

| Задача | Размещение |
| --- | --- |
| Личная страница над списком репозиториев | Публичный `LOGIN/LOGIN`, файл `/README.md` |
| Описание конкретного проекта | `README.md` в репозитории проекта |
| Самостоятельный сайт с навигацией | GitHub Pages или существующая площадка сайта; карточка подключается по публичному адресу |

Для профиля название репозитория совпадает с именем аккаунта. Например, пользователю `octocat` нужен `octocat/octocat`. Корневой README должен содержать текст. Эти условия описаны в [документации профиля](https://docs.github.com/en/account-and-profile/how-tos/profile-customization/managing-your-profile-readme).

Внутри страницы полезно разместить имя, сферу работы, направления проектов, примеры публичных результатов, карточку активности и профессиональные ссылки. Биографию и ссылки заполняют для нового владельца. Данные Юрия в исходном профиле служат примером содержания.

## 4. Охват репозиториев

Сначала определите, что означает «учитывать всё». Видимость репозитория и состояние работы представляют собой разные признаки.

| Признак | Что означает | Поведение исходного генератора |
| --- | --- | --- |
| Публичный | Содержимое доступно посетителям | Включается при наличии в доступном списке |
| Приватный | Доступ назначается владельцем | Включается при доступе токена |
| Внутренний, `internal` | Видимость в пределах предприятия GitHub | Отдельного счётчика нет; используется логическое поле `private` |
| Архивный, `archived=true` | Репозиторий переведён в архив | Исключается из счётчиков репозиториев, языков и категорий |
| Ответвление, `fork=true` | Копия другого репозитория | Отдельного исключения в списке репозиториев нет |
| Завершённый проект | Работа закончена по решению автора | Требует отдельного правила, если репозиторий остаётся обычным |
| Репозиторий организации | Принадлежит организации | Доступ определяется участием пользователя, токеном и правилами организации |

Шаблон получает список через `/user/repos` с `visibility=all` и `affiliation=owner,collaborator,organization_member`. Обрабатываются все страницы по заголовку `Link`. Это список проектов с явным доступом пользователя, которому принадлежит токен; параметры перечислены в [документации репозиториев](https://docs.github.com/en/rest/repos/repos#list-repositories-for-the-authenticated-user).

Публичные проекты, в которых автор когда-либо участвовал, могут выходить за этот список. Глобальный поиск коммитов и запросов на слияние имеет собственную область поиска. Поэтому счётчик репозиториев и счётчик коммитов в исходной реализации описывают разные совокупности.

Установка `GH_METRICS_USER=alice` меняет автора поисковых запросов. Перечисление `/user/repos` по-прежнему относится к владельцу токена. При переносе используйте токен того же пользователя или явно адаптируйте область сбора.

## 5. Источники показателей

### Репозитории

`accessible_repositories` содержит число доступных репозиториев после исключения архивов. `public_repositories` и `private_repositories` делят этот список по полю `private`. В обычном аккаунте сумма двух групп совпадает с общим числом.

`active_repositories` содержит число репозиториев, у которых `pushed_at` попадает в период. Отправка изменений другим участником также делает репозиторий активным. Этот показатель характеризует проекты, в которых есть движение.

### Авторские коммиты

Основной запрос:

```text
GET /search/commits
q=author:LOGIN author-date:>=YYYY-MM-DD
per_page=1
```

Сохраняются `total_count` и `incomplete_results`. Значение `per_page=1` сокращает объём ответа: общее число берётся из `total_count`, а сведения об отдельном найденном коммите отбрасываются.

Поиск охватывает индексируемые основные ветки доступных проектов. Фильтры `author` и `author-date` описаны в [документации поиска коммитов](https://docs.github.com/en/search-github/searching-on-github/searching-commits). Перебор всех веток требует отдельного алгоритма, приведённого в разделе 12.

Исходный запрос задаёт нижнюю границу с точностью до даты и включает всё более позднее. При строгой отчётности задавайте обе границы периода и единую временную зону. Ограничение выдачи поиска в 1 000 объектов относится к получению списка; брать первую тысячу вместо `total_count` для карточки было бы ошибкой. Флаг неполного результата требует отдельной проверки. Правила описаны в [документации поиска API](https://docs.github.com/en/rest/search/search#search-commits).

### Календарь вкладов

Генератор дополнительно запрашивает GraphQL `contributionsCollection`:

```text
totalCommitContributions
totalPullRequestContributions
restrictedContributionsCount
```

Календарь GitHub применяет собственные критерии вкладов. Например, учитывает связь автора коммита с аккаунтом и подходящую ветку. Подробности приведены в [правилах вкладов](https://docs.github.com/en/account-and-profile/reference/profile-contributions-reference).

В проверенном снимке поиск вернул 9 406 коммитов, а `totalCommitContributions` равнялся 177. В исходном генераторе это отдельный диагностический показатель. `restrictedContributionsCount=9654` тоже хранится отдельно: он описывает вклады с ограниченной видимостью. Сложение этого значения с числом коммитов создаёт повторный учёт.

При сбое поиска исходный генератор подставляет значение календаря и отмечает `metric_sources.commits=contribution_graph_fallback`. Переносимый сценарий из комплекта отклоняет такую подмену до публикации, чтобы подпись карточки сохраняла один смысл.

GraphQL вызывается первым. Его общий сбой приводит к заглушке даже при доступном REST API. Для периода больше года потребуется разбиение запроса вкладов на поддерживаемые интервалы и явная агрегация.

### Запросы на слияние

Запрос на слияние изменений (pull request, PR) считается через `/search/issues`:

```text
type:pr author:LOGIN created:>=YYYY-MM-DD
```

Фильтр состояния отсутствует. Учитываются созданные запросы, включая открытые, закрытые и принятые, в доступной области поиска. Это показатель созданных предложений изменений; для числа принятых изменений нужен другой фильтр и соответствующая подпись.

При ошибке исходник использует резервное значение календаря. Проверка переносимого сценария отклоняет этот резервный источник. Исходный генератор сохраняет флаг неполноты только для поиска коммитов; для строгого контроля поиска PR добавьте такой же флаг и его проверку.

### Языки и направления

Языки собираются из `/repos/{owner}/{repo}/languages` в байтах кода. Проценты показывают распределение объёма языков в выбранной совокупности. Они характеризуют состав кода проектов, включая код других участников.

В исходнике читаются первые 25 активных репозиториев из списка, отсортированного по `updated`. Все доступные репозитории продолжают участвовать в счётчиках. Ограничение касается языковой выборки и помогает ограничить время и число запросов. Управляющая переменная: `GH_METRICS_MAX_LANGUAGE_REPOS`. JSON содержит до шести языков, карточка показывает четыре.

Категории выводятся из названий, описаний, тем и основного языка по словарю `CATEGORY_KEYWORDS`. Это эвристика: подстроки вроде `ai` могут дать случайные совпадения. Один репозиторий может относиться к нескольким группам. Названия категорий представляют собой фиксированный словарь, а исходные названия проектов остаются в памяти сборщика.

## 6. Доступ к приватным проектам

В системе участвуют два разных токена:

| Токен | Назначение |
| --- | --- |
| `GH_METRICS_TOKEN` | Читает проекты, разрешённые пользователю и токену |
| Встроенный `GITHUB_TOKEN` | Записывает готовые файлы в репозиторий, где выполняется Actions |

Права `contents: write` у сценария относятся к встроенному токену. Они сами по себе сохраняют область доступа в пределах репозитория сценария. Для чтения других приватных проектов нужен отдельный доступ. См. [описание GITHUB_TOKEN](https://docs.github.com/en/actions/tutorials/authenticate-with-github_token).

Для одного владельца начните с персонального токена с выборочными правами, fine-grained personal access token. Выберите владельца ресурсов и нужные репозитории. Для списка и языков используется `Metadata: read`; для расширенного обхода истории коммитов потребуется `Contents: read`, запросов на слияние по репозиториям - `Pull requests: read`. Проверьте GraphQL и поиск реальным запуском с выбранным токеном.

Один fine-grained токен ограничен одним владельцем ресурсов. Для нескольких организаций потребуется несколько сборов или другой подход. Классический персональный токен с областью `repo` обеспечивает более широкий доступ, который включает возможности записи. Использование такого токена в сборщике только для чтения сохраняет широту его реальных прав. Учитывайте разрешения организации и авторизацию через единый вход (SSO). Возможности и ограничения описаны в [документации токенов](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/managing-your-personal-access-tokens).

Для длительной организационной интеграции подходит GitHub App с нужными установками и правами чтения. Токен установки требует адаптации исходника: вместо `/user/repos` используют список репозиториев установки, а персональные данные вкладов собирают подходящим пользовательским доступом. Такая адаптация является отдельным вариантом реализации.

Сохраните выбранный токен в репозитории профиля:

1. Откройте `Settings → Secrets and variables → Actions`.
2. Выберите `New repository secret`.
3. Имя секрета: `GH_METRICS_TOKEN`.
4. Значение вставьте в поле секрета.
5. Запишите срок действия в свою систему обслуживания доступов.

Значение токена остаётся в хранилище секретов. В README, адрес изображения, исходники и переписку попадает только имя переменной. Создание токена и выдачу доступа выполняет владелец аккаунта либо уже настроенный уполномоченный инструмент.

## 7. Установка из комплекта

В архиве скилл расположен в папке `github-profile-metrics/`:

```text
github-profile-metrics/
  SKILL.md
  agents/openai.yaml
  references/guide.ru.md
  assets/generate_private_metrics.py
  assets/validate_public_metrics.py
  assets/private-metrics.yml
```

Шаблон генератора совпадает с действующим исходником профиля на дату проверки. Шаблон Actions дополнен проверкой результата, ограничением времени и последовательным выполнением обновлений. Эти дополнения относятся к комплекту для переноса.

Для нового аккаунта создайте публичный репозиторий `LOGIN/LOGIN` с README. Склонируйте его и скопируйте файлы из распакованного комплекта. Пример ниже предполагает, что комплект распакован в соседнюю папку:

```bash
git clone git@github.com:LOGIN/LOGIN.git
cd LOGIN
mkdir -p scripts assets .github/workflows
cp ../github-profile-metrics/assets/generate_private_metrics.py scripts/
cp ../github-profile-metrics/assets/validate_public_metrics.py scripts/
cp ../github-profile-metrics/assets/private-metrics.yml .github/workflows/
```

Замените `LOGIN` своим именем аккаунта. В сценарии `GH_METRICS_USER` автоматически получает `${{ github.repository_owner }}`. Для README проекта под организацией задайте конкретный личный аккаунт явно: организация сама по себе не является автором коммитов.

Параметры генератора:

| Переменная | Значение в сценарии | Назначение |
| --- | --- | --- |
| `GH_METRICS_USER` | Владелец репозитория | Автор коммитов, PR и вкладов |
| `GH_METRICS_DAYS` | `365` | Скользящий период активности |
| `GH_METRICS_MAX_LANGUAGE_REPOS` | `25` | Размер языковой выборки |
| `GH_METRICS_TOKEN` | Секрет Actions | Доступ для сбора |

Исходный Python-файл имеет запасное значение пользователя `xyster3k`. Сценарий переопределяет его переменной. Для локального запуска также задайте свой аккаунт явно.

Для работы используется Python 3.11 или новее; шаблон устанавливает Python 3.12. Зависимости генератора входят в стандартную библиотеку.

Ветка в шаблоне называется `main`. При другом имени измените фильтр `push.branches`, адрес карточки и команды публикации. Расписание выполняет сценарий из основной ветки репозитория.

## 8. Первый запуск

1. Добавьте секрет `GH_METRICS_TOKEN`.
2. Отправьте файлы в основную ветку.
3. Откройте `Actions → Profile metrics → Run workflow` либо дождитесь запуска по изменению сценария.
4. Убедитесь, что выполнились сбор, проверка и запись файлов.

Пример отправки файлов:

```bash
git add README.md scripts/generate_private_metrics.py scripts/validate_public_metrics.py .github/workflows/private-metrics.yml
git commit -m "Add aggregate GitHub profile metrics"
git push origin main
```

В комплекте проверка останавливает публикацию, если сборщик записал заглушку, поиск коммитов вернул неполный результат, либо источник коммитов или PR сменился на календарь. Последняя корректная карточка остаётся в опубликованной ветке. Первый успешный запуск создаёт файлы `assets/` автоматически.

Если требуется локальная проверка реального токена, введите его скрытым вводом в Bash:

```bash
export GH_METRICS_USER='LOGIN'
read -r -s -p 'GitHub token: ' GH_METRICS_TOKEN
printf '\n'
export GH_METRICS_TOKEN
python3 scripts/generate_private_metrics.py
python3 scripts/validate_public_metrics.py assets/private-metrics.json assets/private-metrics.svg
unset GH_METRICS_TOKEN
```

Выполняйте локальный запуск в отдельной рабочей копии, если важно сохранить текущие файлы. Генератор перезаписывает JSON и SVG до проверки; сценарий защищает опубликованный результат тем, что останавливается перед commit и push.

Расписание `17 3 * * *` означает ежедневный запуск в 03:17 UTC. Фактическое выполнение может задерживаться. Для публичных репозиториев GitHub также отключает расписание после 60 дней отсутствия активности. Эти особенности приведены в [документации расписаний](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule).

Событие `push` в шаблоне ограничено файлами сценария и двух скриптов. Коммит готовых карточек не запускает новый сбор по этому фильтру. Изменение только README также оставляет сбор до следующего расписания или ручного запуска.

## 9. Подключение карточки

Вставьте в README обычное изображение, заменив `LOGIN`:

```markdown
## Активность разработки

![Сводная активность публичных и приватных проектов](https://raw.githubusercontent.com/LOGIN/LOGIN/main/assets/private-metrics.svg)

Карточка обновляется ежедневно. Показатели учитывают доступные сборщику проекты; сведения о приватных репозиториях публикуются в сводном виде.
```

Для README внутри того же репозитория допустима относительная ссылка `assets/private-metrics.svg`. Абсолютный адрес удобен при переносе блока в другое место.

GitHub может показывать изображение через свой промежуточный кеш. Если данные в JSON и исходном SVG свежие, а профиль показывает старое изображение, проверьте адрес картинки в HTML профиля и сам ответ по этому адресу. Для однократного обновления адреса можно изменить параметр версии, например `?v=20261105`. Параметр обновляет адрес в кеше; ежедневный пересчёт выполняет Actions.

## 10. Проверка публикации

Проверяйте результат по всей цепочке:

1. В Actions есть завершённый запуск нужного сценария и ветки.
2. JSON содержит свежее `generated_at`, ожидаемые `user` и `days`, а `setup_needed` равно `false`.
3. В `metric_sources` указан `commits=commit_search_author_date`, `pull_requests=issue_search_author_created`, `commit_search_incomplete=false`.
4. Количество приватных репозиториев соответствует ожидаемому охвату. Один известный приватный проект доступен сборщику; сверку его идентификатора выполняют внутри доверенного процесса.
5. Сумма публичных и приватных репозиториев совпадает с общим числом; число активных укладывается в общее.
6. SVG имеет корректную структуру XML, цифры совпадают с JSON, изображение открывается по публичному адресу.
7. Страница профиля показывает именно эту картинку. Подписи читаются на компьютере и телефоне.
8. В публикуемых JSON, SVG и изменениях Git содержатся только согласованные поля.

Сам по себе зелёный статус исходного сценария подтверждает выполнение процесса. Старый генератор при ошибке записывает заглушку и возвращает код 0. Поэтому состояние JSON входит в обязательную проверку. Дополнительный проверяющий скрипт из комплекта закрывает этот случай перед публикацией.

## 11. Динамика во времени

Выберите подходящий вид динамики. Каждый отвечает на свой вопрос.

### Календарь GitHub

В профиле над календарём откройте `Contribution settings` и включите `Private contributions`. Посетители увидят количество вкладов по дням с учётом доступного GitHub приватного вклада; сведения о проектах сохраняют установленную видимость. См. [настройку приватных вкладов](https://docs.github.com/en/account-and-profile/how-tos/contribution-settings/manage-visibility-settings-for-private-contributions-and-achievements).

Этот календарь управляется GitHub отдельно от собственной карточки. Изменение настройки календаря сохраняет прежний охват токена сборщика.

### Сравнение периодов

Для сравнения активности соберите отдельные интервалы: последние 30 дней и предыдущие 30 дней, либо завершённые календарные месяцы. У каждого интервала должны быть фиксированные начало и конец. Публикуйте сумму для каждого интервала и изменение между сопоставимыми периодами.

Для месячных значений запрос может использовать `author-date:2026-10-01..2026-10-31`. До формирования отчёта проверьте трактовку границ и временной зоны выбранным API. Если собирается точный список событий, группируйте его по определённой дате автора или дате отправки, сохраняя единую методику.

### История ежедневных снимков

Для графика годового показателя сохраняйте историю снимков. Это расширение к текущему генератору. Пример строки файла `assets/metrics-history.jsonl`:

```json
{"date":"2026-11-05","generated_at":"2026-11-05T10:52:42Z","window_days":365,"commits":9406,"public_repositories":9,"private_repositories":63,"active_repositories":63,"scope_version":1}
```

Порядок записи:

1. Соберите показатели и проверьте успешность и полноту выбранных источников.
2. Выделите дату UTC из времени формирования.
3. Замените запись за ту же дату, если запуск повторный; для новой даты добавьте запись.
4. Упорядочьте историю по дате.
5. Постройте SVG графика из истории и сохраните историю и график одним коммитом.
6. При пропущенном дне покажите разрыв или явно подпишите интервал. Служебная ошибка сохраняет последнее успешное значение и время его формирования.

Разность соседних годовых снимков показывает изменение скользящего окна. За сутки в окно входят новые коммиты и выходят старые; также меняются права доступа и индекс GitHub. Для числа коммитов за конкретный день нужен запрос именно этого дня.

При изменении набора организаций, токенов, архивной политики или определения метрики увеличьте `scope_version` и обозначьте изменение методики на графике. Тогда скачок охвата будет понятен читателю.

Для восстановления прошлых снимков можно пройти историю `assets/private-metrics.json` в Git, извлечь каждую успешную версию и сгруппировать по `generated_at`. В этом профиле ежедневные коммиты уже сохраняют прошлые состояния. Такой ряд описывает наблюдавшиеся значения карточки на даты сборов. Историю публикаций до первого сохранённого снимка получают отдельными запросами к событиям.

## 12. Архивы, ветки и организации

### Архивные проекты

Если требуется учитывать завершённую работу целиком, заведите отдельные показатели:

```text
repositories_total
repositories_current
repositories_archived
repositories_public
repositories_private
```

Стройте `repositories_total` по полному доступному списку, затем разделяйте его по `archived`, `private` и при необходимости `visibility`. Для языков и активности выбирайте нужную подгруппу явно.

В текущем коде исключение архивов применяется к списку репозиториев, языкам и категориям. Глобальные запросы коммитов и PR выполняются отдельно и этого фильтра из Python не наследуют. При необходимости одинакового охвата используйте явное ограничение репозиториями или отдельные запросы и укажите методику на странице.

### Все ветки

Для строгого учёта коммитов во всех ветках:

1. Получите все нужные репозитории и ветки с обработкой страниц.
2. Для каждой ветки получите коммиты за период, передав `sha` и фильтр автора.
3. Объедините результаты по идентификатору коммита (SHA). Один коммит часто входит в несколько веток.
4. Выберите правило для ответвлений: уникальный коммит во всём портфеле или появление коммита в каждом проекте. Это разные метрики.
5. Опубликуйте итоговые количества и описание охвата. Идентификаторы и ветки приватных проектов остаются внутри сборщика.

Такой обход требует больше запросов. Учитывайте ограничения API и повторы после временных ошибок. Удалённые ветки, переписанная история и проекты с утраченным доступом ограничивают доступную историю. Для непрерывного учёта сохранённых событий потребуется отдельное доверенное хранилище.

### Несколько организаций

Для нескольких пользовательских токенов одного автора можно собрать объединённый список проектов по устойчивому числовому `id`. Для коммитов объединяйте идентификаторы либо задавайте непересекающиеся области поиска. Суммирование глобальных `total_count` от нескольких токенов создаёт повторный учёт общедоступных и пересекающихся проектов.

Данные разных владельцев собираются с отдельными секретами. Переносимый шаблон поддерживает один пользовательский токен; объединение нескольких областей требуется реализовать явно. Публично достаточно описать охват и показать общие числа.

## 13. Защита приватных сведений

На выходе полезно разрешить конкретный набор полей: время, аккаунт, период, сводные количества, источники метрик, фиксированные категории и названия языков. Внутри публичного результата оставляйте только эти сведения.

Исходные ответы `/user/repos`, поиска коммитов и PR содержат названия, адреса, сообщения и прочие сведения. Обрабатывайте их внутри процесса. Сценарий записывает в Git только подготовленные файлы `assets/private-metrics.json` и `assets/private-metrics.svg`.

Проверьте также журналы, прикреплённые результаты Actions, временные файлы, поля ошибок и описание коммитов. Полный ответ API или исключение с адресом приватного проекта может раскрыть сведения через журнал публичного репозитория.

Обычный SVG содержит только локальные элементы изображения и экранированный текст. Внешние адреса, сценарии и данные авторизации в нём отсутствуют. Проверка из комплекта контролирует поля JSON, числовые значения, допустимые категории, отсутствие внешних ссылок SVG и соответствие его текстов данным. После изменения оформления адаптируйте проверку к новой схеме.

Сводные числа тоже требуют согласованного уровня детализации. Для чувствительных портфелей можно публиковать укрупнённые группы, более редкие обновления или диапазоны. Идентифицирующие сведения о конкретных клиентах добавляются только в пределах явно разрешённой публикации.

## 14. Ошибки и восстановление

| Симптом | Что проверить | Действие |
| --- | --- | --- |
| `setup_needed=true`, причина `missing_token` | Наличие секрета и передачу в шаг генератора | Добавить или исправить `GH_METRICS_TOKEN`, запустить снова |
| `token_or_api_error` | Срок токена, права, доступ организации, GraphQL и ограничения API | Проверить каждый запрос внутри доверенного процесса; публично записать код ошибки и этап |
| Приватных проектов меньше ожидаемого | Выбранного владельца, набор репозиториев, авторизацию организации, архивы | Сверить доступ к одному ожидаемому проекту и полный список |
| Число коммитов резко упало | `metric_sources.commits`, флаг неполноты, изменение прав | Восстановить основной источник, повторить сбор |
| Actions зелёный, карточка показывает нули | `setup_needed` в JSON | Проверить реальный сбор; подключить проверяющий шаг из комплекта |
| Картинка старая, JSON свежий | Исходный SVG, адрес в README и кеш картинки профиля | Сопоставить ответы, при необходимости обновить параметр версии |
| Автоматическая запись отклонена | `contents: write`, правила ветки и ограничения Actions | Использовать разрешённый проектом способ записи, при необходимости запрос на слияние |
| `non-fast-forward` при push | Изменения ветки во время сбора | Получить актуальную ветку, повторить генерацию поверх неё и отправить обычный коммит |
| Расписание перестало запускаться | Включён ли сценарий, основную ветку и историю запусков | Включить сценарий и проверить ручной запуск |
| Ошибка 403 или 429 | Ограничение частоты, права и заголовки ответа | Различить причину; выдержать указанное время перед новым запросом |

В журнал записывайте этап, длительность, код ответа, количество обработанных страниц и итоговый статус. Фильтруйте секреты и идентифицирующие сведения до вывода. При повторяющейся ошибке сначала выясните её причину.

Сценарий из комплекта последовательно выполняет обновления одной группы. Внешний коммит всё равно может вызвать конфликт при отправке. В таком случае сохраните обычную историю и повторите сбор с актуальной основной ветки. Принудительная перезапись истории для карточки не требуется.

## 15. Изменение оформления

Оформление сосредоточено в `render_svg(metrics)`. Сбор и структура JSON могут остаться прежними. Автор страницы самостоятельно выбирает цвета, шрифты, композицию и набор показателей.

При изменении карточки:

- Согласуйте подписи с источниками и областью подсчёта.
- Покажите период и время последнего успешного формирования.
- Используйте переносы или несколько строк для длинных подписей и категорий.
- Проверьте светлую и тёмную темы страницы, ширину около 375 пикселей и обычный настольный экран.
- Сохраните содержательный альтернативный текст изображения.
- Проверьте итоговый SVG и правила проверяющего скрипта.

Исходная карточка имеет размер 648 × 278 и фиксированные текстовые позиции. На маленьком экране длинные строки могут стать слишком мелкими. Для другого набора языков и категорий предусмотрите перенос текста либо отдельную компактную карточку. Изменение геометрии изображения само по себе сохраняет прежнюю методику расчётов.
